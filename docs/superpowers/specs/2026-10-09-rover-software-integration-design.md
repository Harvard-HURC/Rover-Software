# Rover software integration: one workspace for the rover and its simulation

Date: 2026-10-09. Status: design approved by the user, section by section; implementation not started.

## 1. Goal

Make the simulation easy to use with different rover programs, make the rover easy to change in one place,
and make the code easy for a student team to contribute to. Concretely:

- The same rover programs (driver, autonomy, mission code) run unchanged on the simulated and the real rover.
- One standard rover description is the single source of truth for the rover's geometry, joints, masses,
  motors and sensors; the simulation, RViz and the driver all read it.
- The work lives in the team's repository, [Harvard-HURC/Rover-Software](https://github.com/Harvard-HURC/Rover-Software),
  under its conventions, with CI and contributor documentation.

Not in scope: new simulation features, the robotic arm, choosing the real motor controllers, the base-station
radio link.

## 3. Starting point

**The team repository** (4 commits by Beckett O'Brien, 2026-10-02 to 10-05) is a skeleton:

- The repository is the `src/` folder of a colcon workspace (clone into `<ws>/src/`); packages sit at its top level.
- `rover_description` and `rover_sim`: empty `ament_cmake` packages. `rover_sim/launch/gazebo.launch.py` starts
  Gazebo, as separate server and GUI on macOS. Its non-macOS branch uses the undefined name `pkg_ros_gz_sim`
  (the variable is `gz_pkg`), so it fails on Linux and Windows.
- `pixi.toml`: RoboStack Jazzy, platforms `osx-arm64`, `win-64`, `linux-64`; `ros-jazzy-desktop`, `ros_gz`,
  `ros-dev-tools`; on macOS `GZ_IP=127.0.0.1` and `GZ_TRANSPORT_LOCALHOST_ONLY=1`.
- README rules: a branch and a reviewed pull request for every change, never push to `main`; describe every
  new package in the README.

**This repository** (89 commits, no remote): the URC simulation in `sim/` (Gazebo plugins, the URC world
generator `sim/urc/`, the driver station, launcher and referee, 495 tests), the rover model generated by
`sim/gen_model.py` (Python `Params`/`DriveParams` to `sim/models/rover/model.sdf`), the superseded swerve
kinematics library `driver/`, `docs/`, and `papers/` (four journal PDFs).

What is coupled today:

1. The rover description is Python inside the simulation, and its geometry is typed again in
   `driver/include/rover_driver/config.hpp` (`kRover`).
2. The simulation owns the wheel control: `RoverDrivetrain` turns a body twist into wheel speeds and runs the
   motors' speed loops, so a team driver cannot be tested against it.
3. The driver has no ROS node and no link to the simulation.
4. The station, referee, judge and world generator import `gen_model` directly.

## 4. Packages

```
Rover-Software/                cloned into <ws>/src/
├── pixi.toml, pixi.lock       the team's environment, extended for the simulation; osx-arm64, linux-64, win-64
├── README.md                  quick start, package list, contributing rules (the team's, extended)
├── CONTRIBUTING.md, .github/  CI, CODEOWNERS, PR template
├── docs/                      architecture, design specs, simulation manual, research notes
├── rover_description/         the rover: config/rover.yaml, urdf/*.xacro, meshes/, launch/view.launch.py
├── rover_sim/                 the simulation and its tools (driver station, launcher, referee)
└── rover_control/             controller configs, the driver code, the real-hardware stub, rover.launch.py
```

**Dependency rule.** `rover_control` depends on `rover_description`; `rover_sim` depends on both. Nothing
depends on `rover_sim`. The simulation talks to rover code only through ros2_control and topics, never through
its internals. The rover's computer builds `rover_description` and `rover_control` only.

Custom messages are avoided; standard messages are used throughout. If one becomes unavoidable, a
`rover_msgs` package is added then.

## 5. The rover description (`rover_description`)

```
rover_description/
├── config/rover.yaml        every physical number of the rover
├── urdf/rover.urdf.xacro    links, joints, visuals, collisions and sensor frames, built from rover.yaml
├── urdf/ros2_control.xacro  the ros2_control block; the hardware plugin is a xacro argument
├── meshes/                  the tread wheel (today's wheel.glb) and any other meshes
└── launch/view.launch.py    robot_state_publisher + joint_state_publisher_gui + RViz
```

**What goes where.** `rover.yaml` holds physical facts:

- geometry: wheel radius and width, rocker pivots, wheel offsets, chassis size;
- masses and inertias;
- joint limits and damping, and the differential's spring and damper;
- the motors: voltage, kt, ke, resistance, gear ratio, efficiency, current limit, top wheel speed;
- sensor mounts and rates: IMU, GNSS, the camera head and its pan/tilt joints.

How the simulation models the world stays in `rover_sim/config/`:

- the contact model (Stribeck, slip compliance, friction noise);
- dig-in, ruts and tyre sinkage;
- dust;
- the motor model's integration settings.

Every field of today's `Params` and `DriveParams` is sorted by this rule. The motor specs are physical, so they
live in `rover.yaml`; `rover_sim`'s motor model reads them from there.

**ros2_control block.**
- The four wheel joints each have a `velocity` command interface and `position`, `velocity` and `effort`
  (motor current) state interfaces.
- The rocker joints and the camera pan/tilt joints have state interfaces only.
- The hardware plugin defaults to the real hardware (`rover_control`'s stub). The simulation's wrapper sets it
  to `RoverSimSystem`.

**Gazebo-only parts** live in `rover_sim/urdf/rover_sim.urdf.xacro`. It includes the description and adds:
- the `gz_ros2_control` system;
- the sensor definitions (IMU, NavSat, RGB-D, the LED);
- the rocker-differential plugin;
- the drivetrain and motor model;
- the joint monitor;
- the visual-only cues (tread visual switch, dig-in sinkage, ruts).

The description itself names no Gazebo plugin.

**The driver reads `rover.yaml`** through ROS parameters, loaded by the launch files. `kRover` and
`config.hpp` go away.

**Equivalence test** (`rover_sim/test`). The wrapper xacro is expanded and converted to the SDF that Gazebo
loads (`xacro`, then `gz sdf -p`). It is compared numerically with a frozen copy of today's
`sim/models/rover/model.sdf`, kept as a test fixture. The comparison covers:
- every link's mass, inertia and pose;
- every joint's type, axis, limits, damping and pose;
- every collision geometry and pose;
- every sensor's pose and settings;
- every plugin parameter.

Differences must be zero within floating-point tolerance. Two URDF effects are handled explicitly:
- Converting URDF to SDF merges links joined by fixed joints. Links that must stay separate get
  `preserveFixedJoint`, or the frozen reference is compared after the same merge.
- URDF cannot express closed kinematic loops. None is needed: the rocker differential is already a spring
  plugin.

## 6. The drive boundary (ros2_control)

```
 driver station / autonomy / teleop
        │  /cmd_vel  (geometry_msgs/TwistStamped)
        ▼
 controller_manager      config: rover_control/config/controllers.yaml, identical on sim and rover
   ├─ drive controller   diff_drive_controller (left = FL, RL; right = FR, RR) to start; the team's own
   │                     controller replaces it by changing its name in controllers.yaml. Publishes /odom
   │                     and odom→base_link; speed and acceleration limits; cmd_vel timeout
   └─ joint_state_broadcaster → /joint_states (wheels, rockers, camera head)
        │  per-wheel velocity commands    ▲ wheel position, velocity, effort; rocker and head angles
        ▼                                 │
 hardware interface      chosen by the launch file
   ├─ sim:  rover_sim's RoverSimSystem, loaded inside Gazebo by gz_ros2_control
   └─ real: rover_control's stub until the motor controllers are chosen (it reports zero motion, logs the
            commands it would send, and refuses to activate with a clear message if asked to drive)
```

### 6.1 Simulation side

- **`RoverDrivetrain` takes four wheel-speed setpoints** instead of a body twist. The twist-to-wheel
  kinematics, `track_multiplier` and the acceleration ramp move into the drive controller's configuration.
- **Everything a real motor controller does stays in the plugin:**
  - the DC motor model, gearbox, the PI speed loop, the current limit and backlash;
  - a setpoint watchdog: the motors stop when no setpoint arrives within `cmd_timeout`.

  Everything physical behind the setpoints stays as it is:
  - the contact model, dig-in, slip compliance and rolling resistance;
  - the visual cues, odometry and ground truth;
  - the drivetrain state message.
- **`RoverSimSystem`** is a `gz_ros2_control::GazeboSimSystemInterface` plugin in `rover_sim`. It exports the
  interfaces of section 5.
  - `write()`: hands each wheel's setpoint to `RoverDrivetrain` through an entity component on the wheel
    joint, a new `rover_sim` component. It cannot use Gazebo's `JointVelocityCmd`, because the Physics system
    would enforce that as a velocity constraint and bypass the motor model.
  - `read()`: reports joint position and velocity from the ECM, and the motor current as effort.
- **A ROS-free setpoint topic,** `/model/rover/wheel_cmd` (gz-transport), feeds the same component. It is for
  the simulation's own tests and tools. When `RoverSimSystem` is loaded, the topic is ignored and a warning
  says so. The test helpers turn their twist schedules into wheel setpoints with the skid-steer formula the
  plugin uses today, so every calibration test keeps its meaning and numbers.
- **The driver station publishes `/cmd_vel`** (TwistStamped) through rclpy instead of Gazebo's topic, so it
  drives through the controllers. Its sim-only parts keep using Gazebo directly: Fly, Map, the drivetrain
  readout and the referee.
- **The station, referee and judge read rover geometry from `rover.yaml`,** or from the expanded description,
  instead of importing `gen_model`.
- **Worlds no longer include the rover.** The launch file spawns it from `robot_description` at the mission
  sheet's start pose. The ROS-free test helpers spawn the converted SDF, generated and cached by the test
  harness.

### 6.2 Topic contract (the same names on sim and rover)

| Topic | Type | Publisher |
|---|---|---|
| `/cmd_vel` | geometry_msgs/TwistStamped | operator, autonomy |
| `/odom` | nav_msgs/Odometry | drive controller |
| `/joint_states` | sensor_msgs/JointState | joint_state_broadcaster |
| `/tf`, `/tf_static` | tf2_msgs/TFMessage | drive controller, robot_state_publisher |
| `/robot_description` | std_msgs/String | robot_state_publisher |
| `/imu` | sensor_msgs/Imu | Gazebo bridge / IMU driver |
| `/gps/fix` | sensor_msgs/NavSatFix | Gazebo bridge / GNSS driver |
| `/camera/image`, `/camera/depth`, `/camera/camera_info` | sensor_msgs/Image, CameraInfo | Gazebo bridge / camera driver |
| `/clock` | rosgraph_msgs/Clock | Gazebo bridge (sim only) |
| `/ground_truth/odom` | nav_msgs/Odometry | Gazebo bridge (sim only) |

### 6.3 Launch

- **Simulation:** `rover_sim/launch/sim.launch.py` takes `world:=<name>`, `gui:=false|true`,
  `station:=true|false` and `controller:=<name>`. It does the following:
  - starts the Gazebo server, plus the GUI as a separate process on macOS, as the team's launch file does;
  - loads the world;
  - runs robot_state_publisher on the expanded `rover_sim.urdf.xacro`;
  - spawns the rover;
  - lets gz_ros2_control start the controllers from `rover_control`;
  - starts the sensor bridge;
  - optionally starts the station.

  The launcher's tiles call it.
- **Real rover:** `rover_control/launch/rover.launch.py` starts robot_state_publisher on `rover.urdf.xacro`
  and `ros2_control_node` with the same `controllers.yaml`.

## 7. Environments

- **pixi** (the team's `pixi.toml`) is the one environment.
  - It is extended with the Gazebo development libraries, `ros2_control`, `ros2_controllers`,
    `gz_ros2_control`, `xacro` and the simulation's Python libraries.
  - The lock file is resolved for all three platforms, in one pull request with one owner.
  - Tasks: `pixi run build` (colcon build), `pixi run sim world=<name>`, `pixi run launcher`, `pixi run test`,
    `pixi run fetch-data`.
  - `sim/run.sh` is replaced by the launch files.
- **Windows.**
  - The rover packages, RViz and the ROS tools run natively through pixi (`win-64`).
  - The Gazebo simulation runs in WSL2 (Ubuntu 24.04), with a step-by-step guide in `CONTRIBUTING.md`.
  - `rover_sim` is skipped in native Windows builds.
- **The rover's computer** builds `rover_description` and `rover_control`, with no Gazebo and no GPU.
  - On Ubuntu 24.04: apt ROS 2 Jazzy plus `rosdep` from the packages' `package.xml`.
  - A Jetson on JetPack 6 (Ubuntu 22.04) cannot use apt Jazzy. It would use pixi (`linux-aarch64`) or Docker;
    that is decided when the computer is chosen.
- **Data.**
  - The terrain rasters (USGS 3DEP and lidar, NAIP; about 400 MB) stay out of git. `pixi run fetch-data`
    downloads them from the official public sources and verifies their checksums. It works on a fresh clone
    without `--force`.
  - Generated worlds and models are built locally on first use.
  - The tracked research files (`sim/data/research`, 543 files) move to `docs/research`.

## 8. Collaboration

- **Workflow:** the team's README rules (a branch and a reviewed pull request per change). Branch protection on
  `main` (require CI and one review) needs an admin; the user's account has push but not admin rights.
- **CI** (GitHub Actions; free, the repository is public), on every pull request:

  | Runner | What it runs |
  |---|---|
  | Ubuntu 24.04 | `pixi install`, colcon build of all packages, the driver's unit tests, `xacro` + `check_urdf`, the equivalence test, `rover_sim`'s physics tests headless, and a 30 s smoke test (launch the simulation, publish `/cmd_vel`, check `/odom` moves) |
  | macOS (Apple silicon) | the same, plus the rendering tests (a GPU is available) |
  | Windows | build `rover_description` and `rover_control` |

  Rendering tests are skipped, with a printed reason, where no GPU is available.
- **Documents:**
  - `CONTRIBUTING.md`: setup per platform including WSL2; the branch and PR workflow; how to change the rover,
    add a world, add a sensor, swap the drive controller and run the tests; code style.
  - `CODEOWNERS`, with one owner per package, named by the team.
  - A PR template: what changed, how it was tested, sim or hardware.
  - A short README per package. Today's 86 KB `sim/README.md` becomes `rover_sim/README.md` (a quick start)
    plus `docs/sim/` (the manual, design notes and Gazebo lessons).

## 10. Testing strategy

- **The equivalence test** (5): the rover the simulation loads is the rover of today, number for number.
- **The existing simulation suite** (495 tests, including the drivetrain calibration rows and the visual cue
  tests) must pass unchanged after PRs 1 and 2, and with the twist-to-setpoint helper after PR 3.
- **New tests:**
  - `RoverSimSystem` (setpoints reach the motor model at the right step; state readback);
  - the setpoint watchdog;
  - the tank kinematics library (unit tests);
  - the launch smoke test;
  - `check_urdf` on the expanded description.
- **CI** runs these on every pull request (8).

## 11. Risks

| Risk | Handling |
|---|---|
| The simulated hardware interface: gz_ros2_control loading a custom system and handing setpoints to `RoverDrivetrain` within one physics step | Prototyped first in PR 3, on Mac and Linux, before anything depends on it |
| URDF-to-SDF conversion changes the rover (fixed-joint merging, defaults) | The equivalence test (5) blocks PR 2 until zero differences |
| Jazzy's `diff_drive_controller` takes `TwistStamped` only | The station and docs use `TwistStamped`; teleop tools are run in stamped mode |
| A three-platform pixi lock may not resolve with every simulation dependency | Resolved early in PR 1; a package missing on `win-64` is limited to the simulation's feature (sim is WSL2 there) |
| CI runners have no GPU | Rendering tests run on the macOS runner; Linux runs the physics and smoke tests |
| The team works on the same files during the migration | Small PRs; PR 1 lands first and is announced; owners per package |
| The rover's computer runs Ubuntu 22.04 (Jetson) | pixi `linux-aarch64` or Docker, decided when the computer is chosen |
